= Template Customization

The default UI bundle can be customized using AsciiDoc attributes.
xref:templates.adoc[] explains how to access such attributes.
But what are the attributes that actually used by the templates.
If you're going to use the default UI bundle for your project, you'll want to know.

== page-layout attribute

The `page-layout` attribute is defined per-page and tells Antora which layout to use.
This UI also appends the layout name to the `<body>` tag as a class, which makes it easy to target layouts in CSS.

A common use of the `page-layout` attribute is to select the `article` layout for blog posts.

[,asciidoc]
----
= Blog Post Title
:page-layout: article

Your blog post content starts here.
----

The resulting HTML will include a `<body>` class that matches the layout, allowing layout-specific styling.

== page-pagination attribute

The `page-pagination` attribute is set in your xref:antora:playbook:asciidoc-attributes.adoc[playbook] in order to enable pagination, if your UI bundle supports it.
The default UI bundle supports this and you'll get the links to previous and next pages at the bottom of every page, based your navigation.

.Enable pagination
[,yaml]
----
asciidoc:
  attributes:
    page-pagination: ''
----

Antora automatically calculates the appropriate URLs and inserts the correct links.

Since you most likely want this enabled for every page in your site, there's no point setting this attribute per page.
However, if you do want to be able to override it per page, such as to turn it off, then you need to soft set the value in the playbook.

.Enable pagination, but make it overridable
[,yaml]
----
asciidoc:
  attributes:
    page-pagination: '@'
----

You can now turn page pagination off by unsetting the `page-pagination` attribute in the document header.

== Table of Contents

Article pages (pages using `:page-layout: article`) automatically display a sidebar table of contents built from the section headings in the page.
No configuration is required — any `==` through `======` headings that carry an `id` become TOC entries.

=== How it works

The Antora extension extracts heading structure from the converted HTML of each page during the build.
The result is stored as structured data and passed to the `toc.hbs` partial, which renders the sidebar.
Headings are nested in the sidebar to match their depth in the document (`==` at level 1, `===` at level 2, and so on).

=== Controlling TOC placement in the document body

By default the extension extracts headings without placing a TOC block in the body.
If you want an inline TOC to also appear at a specific point within the article body, set `toc: macro` in your playbook and place `toc::[]` in the document where you want it to appear.

.Enable inline TOC placement in the playbook
[,yaml]
----
asciidoc:
  attributes:
    toc: macro
----

.Place the TOC in the document body
[,asciidoc]
----
= Blog Post Title
:page-layout: article

Opening paragraph.

toc::[]

== First Section

Content here.
----

When `toc::[]` is present, Asciidoctor generates a `<div id="toc">` block at that location.
The extension uses that block as the source of TOC data and removes it from the body, so the inline block does not appear twice.
If `toc::[]` is absent (even with `toc: macro` set), the extension falls back to extracting headings directly from the page HTML.
Either way the sidebar TOC is populated.

NOTE: The `page-toctitle` and `page-toclevels` attributes from the Antora default UI are not used by this UI bundle.
The sidebar heading is fixed in the `article.hbs` layout and all heading levels are always included.
